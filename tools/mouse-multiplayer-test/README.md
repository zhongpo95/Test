# 마우스 좌표 멀티플레이 시험 맵 v002

`Hera_Mouse_Multiplayer_Test_v002.w3x`는 원본 묵시록 맵을 사용하지 않고 생성한 32×32 평지, 6인 시험 맵이다. 기존 RPG 맵과 DLL을 변경하지 않는다. 같은 헤라/JN 실행 환경에서 사람 2~6명이 참가한다. 혼자 실행하면 수신 확인이 1/1이므로 멀티 검증이 되지 않는다.

v002는 시작 대기실에서 각 플레이어를 서로 다른 팀으로 배치한다. v001의 단일 팀 구성으로 게임 시작이 막히던 문제를 수정했다. 게임에 진입한 후에는 시험 유닛이 서로 싸우지 않도록 Lua에서 모든 플레이어를 동맹으로 설정한다. 이전 v001 파일도 보존한다.

## 실행 순서

1. 헤라/JN으로 방을 만들고 최소 두 명이 입장한다. 시작 후 3초 정도 기다려 모두 `LUA READY`를 확인한다.
2. 각자 다른 지점을 가리킨다. 한 명이 `-local`을 입력하고 마우스를 게임 화면의 지형 위로 옮긴다. 1초 후 로컬 좌표가 표시된다.
3. 같은 사람이 `-mouse`를 입력한다. 모든 참가자 화면에서 해당 플레이어 색의 작은 보병 표식이 같은 지점으로 이동하고 `M ACK N/N PASS`가 표시되는지 확인한다. N은 현재 참가 중인 사람 수다. 다른 사람도 차례로 실행한다.
4. `-dz`로 `DzGetMouseTerrainX/Y` 결과도 비교한다. 이 경우 표시 종류가 D다.
5. `-track`으로 10초 동안 커서를 움직인다. 종료 후 `-status`로 마지막 좌표의 수신 확인을 본다.
6. `-order`로 중력건의 입력 경로를 검사한다. 보조 보병을 로컬로 선택하고 `message.mouse()` → `message.order_point(852066, x, y)` → 본래 보병 재선택을 0.1초 간격으로 100회 시도한다. 다른 플레이어는 별도의 색상 표식 이동과 O 수신 확인을 확인한다. 종료 후 모두 `-status`를 입력한다.

명령을 친 뒤에는 커서를 채팅창이나 화면 밖이 아닌 지형 위에 둔다. `-stop`은 자신의 반복 시험을 중단하며 `-help`는 명령 목록을 표시한다. 여러 사람의 시험도 구분되지만 원인 확인에는 한 명씩 실행하는 편이 좋다.

| 명령 | 확인 대상 |
|---|---|
| `-local` | `message.mouse()` 로컬 좌표 읽기. 공유 상태 변경 없음. |
| `-mouse` | 로컬 좌표 한 번 읽기, DzSyncData 전달, 모든 사람의 수신 확인. |
| `-dz` | 대체 Dz 마우스 좌표 API 한 번 읽기 및 전달. |
| `-track` | 0.2초 간격 50회 좌표 전달. |
| `-order` | 중력건과 같은 로컬 선택 및 점 명령 경로, 공유 시전 이벤트 도착. |
| `-status` | M/D/O의 마지막 좌표, 순번, 현재 참가자의 수신 확인 수. |

## 결과 해석

`ACK N/N PASS`는 각 클라이언트가 같은 좌표 메시지 또는 시전 이벤트를 받고 수신 확인을 보냈다는 뜻이다. 실제 커서 위치와 좌표의 일치 여부는 표식을 보고 확인한다. 커서를 계속 움직이는 동안 오래된 메시지의 수신 확인은 무시하므로 종료 후 `-status`를 본다.

O가 표시되지 않으면 점 명령에서 시전 이벤트까지 도달하지 않은 상태다. 실제 엔진은 입력을 합치거나 시전을 취소할 수 있으므로 O 순번이 반드시 100일 필요는 없다. M은 정상인데 O가 안 되거나 사용자가 종료되면 입력 명령 경로를 추가 조사할 근거가 된다. 모든 사람이 좌표와 O 이벤트를 받고 게임에 남아 있어야 해당 환경에서 시험을 통과한 것으로 판단한다.

보조 보병의 A0CJ는 v211 중력건과 같은 ANcl 기반 지점 지정, `innerfire` 명령, 사거리 200000, 재사용 0.01초 설정이다. 원래 중력건의 유닛·아이템 끌어당기기와 이펙트는 이 맵에 포함하지 않는다. 이 맵을 통과해도 원래 중력건 전체가 안전하다는 뜻은 아니다.

## 종료 지점 로그

각 실행 컴퓨터의 작업 디렉터리 아래 `Logs/Hera_Mouse_Test_v002_pN.txt`를 확인한다. 보통 Warcraft III 실행 폴더 아래에 생긴다. 파일 작성이 불가능하면 게임에서 안내한다. 다시 시작하면 해당 시험 로그를 새로 작성하므로 종료된 직후 보관한다.

`BEFORE message.mouse` 뒤에 `AFTER`가 없다면 좌표 읽기 호출 도중 종료되었을 가능성이 있다. `BEFORE message.order_point` 뒤에 `AFTER`가 없다면 점 명령 호출 도중일 가능성이 있다. `AFTER`까지 남아 있어도 이후 엔진 처리나 네트워크 오류로 종료될 수 있다. Lua `pcall`은 DLL 내부의 접근 위반을 잡지 못한다.

## 빌드 및 검증

Windows Python, x64 StormLib.dll, pjass.exe, 해당 게임 버전의 common.j와 Blizzard.j가 필요하다. 출력 파일이 이미 존재하면 빌드는 거부한다. 원본 맵 입력은 받지 않는다.

```powershell
python tools/mouse-multiplayer-test/build.py --output <새로운.w3x> --build-dir <새로운_빌드폴더> --stormlib <StormLib.dll> --pjass <pjass.exe> --common <common.j> --blizzard <Blizzard.j>
python tools/mouse-multiplayer-test/test.py --report <결과.json>
```

모의 검증에는 `lupa`의 Lua 5.3 런타임이 필요하다. 별도 라이브러리 디렉터리는 `--lupa-root`로 지정할 수 있다. 서로 독립적인 Lua VM 6개, 공유 이벤트 큐, 서로 다른 마우스 좌표로 수신 확인과 로컬 입력 분리를 검사한다.

제작 시 수행한 검증은 JASS 컴파일, Lua 5.3 모의 실행, W3I/W3E/WPM/W3A 구조 검사, MPQ 내부 파일 원문 대조다. 실제 게임 실행, 화면 검사, 실제 헤라 서버 멀티플레이와 DLL 호출 안정성 검증은 아직 수행하지 않았다.
