# 원정 동기화 검사

## 확인된 장애와 수정 경계

캐릭터 선택 뒤 `SetMapLine(pid)`의 로컬 분기에서 `ExpUIOpen`을 거쳐
`TriggerExecute(ExpRefresh)`를 선택한 클라이언트만 호출했다.
PR #113은 창 열기를 로컬 표시 상태 변경으로 제한하고 모든 클라이언트가 같은
0.10초 타이머 이벤트에서 화면을 갱신하도록 변경했다.
게임 상태를 바꾸는 선택/구매/스탯 요청은 `DzSyncData("ExpCmd", ...)`와 동기화 수신부를 사용한다.

2026-09-20의 `14.32.54.log`와 `14.32.58.log`를 비교했다.
각 파일에 `[ARC-PICK-v1]` 기록 173개가 있었고, 클라이언트별 UI 기록을 제외한
선택 단계/상태 기록 167개가 서로 대응했다. 대응 키는 선택 순서, 경과 초, 플레이어,
기록 단계이며 대응 기록의 내용 차이와 누락은 없었다.
두 클라이언트 모두 나루메아와 반디 선택 후 마지막 선택의 20초 진단까지 도달했다.
이는 기존 선택 직후 장애 구간의 통과 근거이며, 원정 전체의 무결성을 증명하는 체크섬은 아니다.

## PR 자동 검사

`.github/workflows/expedition-checks.yml`은 main 대상 PR과 main 변경마다 다음을 실행한다.

```text
node tools/check-expedition-sync.cjs
node tools/check-expedition.cjs
node tools/check-expedition-ui.cjs
node tools/check-ui-input-startup.cjs
node tools/check-pick-trace.cjs
```

`check-expedition-sync.cjs`는 `Import.j`에 등록된 소스를 읽는다. 원정 UI와 지도에서
로컬 플레이어를 읽는 함수, 프레임/키 콜백, `ExpRefresh` 렌더 콜백을 시작점으로
일반 JASS 함수 호출을 다른 파일까지 추적한다. 새 콜백도 자동으로 검사한다.
명시적으로 검토한 화면 API, 조회 API, 동기화 송신과 UI 상태 변수만 허용한다.
미검토 호출과 다른 전역 변수 쓰기는 함수 경로 및 소스 줄 번호를 출력하며 실패한다.

금지 동작을 메모리상의 소스에 삽입해 검사기 자체도 검증한다.

- 직접/보조 함수를 통한 `TriggerExecute`, 문자열 `ExecuteFunc`.
- 유닛 상태 변경, 공유 난수 호출, 타이머 핸들 생성.
- 공유 골드 배열 변경과 새 미검토 API.
- 다른 라이브러리의 조회 함수에 추가한 상태 변경.
- `GetLocalPlayer`가 없는 새 프레임 콜백의 위험한 호출.

실제 파일이나 맵에 위 금지 코드를 쓰지 않는다. 동기화된 게임 로직의 정상적인
`TriggerExecute`와 초기 UI 생성까지 일괄 금지하는 검사는 아니다.
기존 UI 모의 실행은 선택자/미선택자/관전자, 창 열기/닫기, 구매/배분 요청을 확인하고,
입력 검사는 모든 클라이언트에서 동일한 입력 등록 순서를 확인한다.

## 검사 범위와 변경 시 원칙

- 정적 검사와 JS 모의 실행이며 Warcraft 엔진 실행이나 JASS 컴파일을 대체하지 않는다.
- 일반 함수 호출을 대상으로 한다. 미해석 호출은 허용하지 않지만 전체 vJASS 문법,
  모든 로컬 분기, 변수의 흐름, 외부 DLL의 구현을 검증하는 분석기는 아니다.
- `StashLoad`는 기존 로컬 저장소의 조회 경계로 허용한다. 내부 scratch 변수와
  저장 엔진은 추적하지 않는다. 저장/업로드 함수는 UI 표시 경로에서 허용하지 않는다.
- 원정 본체의 기존 소유자별 보상 저장과 카메라 분기는 이 UI 호출 경로 검사 밖이다.
  저장값을 공유 게임 상태에 적용할 때는 반드시 동기화 수신 경계를 별도로 검토한다.
- 허용 목록을 늘릴 때는 호출자의 실행 범위와 보조 함수의 부작용을 확인한다.
  검사 통과를 위해 게임 상태 변수나 실행 API를 허용 목록에 추가하지 않는다.
- 로컬 UI 변수는 공유 게임 판정에 사용하지 않는다. 이 역방향 데이터 흐름은 별도 리뷰가 필요하다.
- 자동 실행과 병합 차단은 다르다. 필수 상태 검사 설정이 없는 저장소에서는
  실패한 PR도 병합할 수 있으므로 PR에서 이 검사 결과를 확인한다.

## 실제 멀티플레이 확인 범위

이번 로그에서 확인한 것은 두 캐릭터 선택과 이후 20초 구간이다.
상점/스탯/이벤트/보스 전환/결과/보상 저장은 다음 실제 플레이에서 별도로 확인한다.
특히 한 명이 아직 선택하지 않은 상태, 서로 다른 창을 열거나 접은 상태,
선택/구매 시점이 다른 상태에서 진행해야 한다.
실패 시 양쪽 런타임 로그와 사용한 맵의 빌드 시점을 함께 남긴다.
현재 선택 진단은 20초로 제한되어 있으므로 뒤의 전투/보상 오류는 해당 경계에 진단이 필요하다.
맵 파일 생성과 실제 게임 실행은 이 자동 검사에서 수행하지 않는다.
